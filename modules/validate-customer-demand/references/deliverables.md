# K1 交付契约

最终结果按以下固定顺序交付。每一项只使用本轮事实、弱线索、工作假设和证据缺口；没有依据的格子写“待验证”，不为填满结构造事实。

## 1. 业务类型

写明 To B、To C 或混合业务，以及混合业务本轮实际分析的是企业/渠道客户还是最终个人用户。业务类型尚不清楚时写“待验证”。

## 2. 客户细分依据

说明本轮选用的一种主要细分逻辑、它要解决的最大不确定性，以及该判断来自哪些已发生行为或仍只是工作假设。

## 3. 候选客群

逐个列出候选客群的规范短标签、身份/状态、任务场景、购买动机、取舍标准、现实替代或行为线索、当前证据和证据缺口。证据不足时明确标为“候选客群”。

| 候选客群 | 身份/状态 | 任务场景 | 购买动机 | 取舍标准 | 行为证据 | 证据缺口 |
| --- | --- | --- | --- | --- | --- | --- |
| 规范短标签 | 基于本轮证据或“待验证” | 基于最近事件或“待验证” | 已确认或“工作假设” | 已确认或“待验证” | 已发生行为或“待验证” | 会改变 Target 的信息 |

客群标签要回答“谁为什么买”，不能只回答“从哪里买”或“买什么技术”。技术路线、购买渠道和产品品类可放入场景或证据列，不得单独作为候选客群。

## 4. Target 筛选

同时展示下列三个位置及其取舍依据：

| Target 位置 | 当前客群 | 取舍依据与证据状态 |
| --- | --- | --- |
| 优先目标客群 | 基于本轮证据填写；未知写“待验证” | 已发生行动、替代成本、可触达性或“待验证” |
| 备选客群 | 基于本轮证据填写；未知写“待验证” | 当前不能优先验证的原因或“待验证” |
| 暂不选择客群 | 基于本轮证据填写；未知写“待验证” | 本轮不纳入验证的理由或“待验证” |

To C 时，Target 表的“当前客群”列只写规范短标签；“候选”“优先验证”等状态写入“取舍依据与证据状态”列，不用括号或后缀改写客群名称。
“取舍依据与证据状态”必须说明客户动机、取舍标准和当前证据，不用渠道占比、某技术产品或某品类有销售单独证明 Target 成立。

优先 Target 还必须填写五项有效细分闸门；每一格写 `[已确认]`、`[假设]` 或 `[缺口]`，不计算总分：

| 可衡量 | 足够价值 | 可触达 | 可区分 | 可行动 |
| --- | --- | --- | --- | --- |
| 能否一致识别 | 是否值得继续投入验证 | 能否找到并继续验证 | 是否有可观察差异 | 能否执行下一验证动作 |

Target 初判后，完整交付默认生成 K1 HTML 行动报告并内嵌 [STP 客群收窄画布](visual-frameworks.md#stp-客群收窄画布)，再紧接输出一张已填写的 [价值设计画布（K1 客户细分定位）](visual-frameworks.md#价值设计画布k1-客户细分定位)。单独画布可输出 SVG。用一到三句话说明最关键判断和最大证据缺口。价值设计画布标题必须显式写为 `价值设计画布（K1 客户细分定位）`，不得只输出无标题表格。只在最大证据缺口需要时，至多再选择一张辅助框架。

完整 HTML 还必须在画布前显示一个 `consultant_insight` 对象。三个字段都要以 `[已确认]`、`[假设]` 或 `[缺口]` 开头；每次只呈现一个锐见形成的判断，不展示方法库：

```json
{
  "consultant_insight": {
    "contrarian": "[假设] 关键反常识",
    "do_not_do": "[假设] 本轮明确不做",
    "reversal_evidence": "[缺口] 改判证据"
  }
}
```

旧输入未提供该对象时，渲染器用现有核心判断、非目标客户和停止线生成兼容展示；这只是显示兼容，不替代后续交付应明确填写三个字段。

## 5. 客户问题定位假设

写成“对哪类客户，在什么具体场景下，要完成什么高优先级任务或解决什么问题；客户当前如何替代，以及为什么值得继续验证”。这只是可推翻的 K1 假设，不写产品/服务、痛点缓解、收益创造或最终价值主张。

## 6. 非目标客户

对每个优先目标客群，列出相似但不属于本轮 Target 的非目标客户及可验证排除理由，例如没有共同场景、没有现实替代行为、角色链无关或交付条件不匹配；无依据时写“待验证”。

## 7. 验证与回传

### 需求证据地图

| 字段 | 当前内容 |
| --- | --- |
| 已确认行动 | 已发生的时间、材料、安排、试用、采购或付费行为；未知写“待验证” |
| 弱线索 | 只表达兴趣、赞同或抱怨的内容；未知写“待验证” |
| 工作假设 | 对需求的可推翻解释；未知写“待验证” |
| 最大证据缺口 | 下一次行动必须带回的证据；未知写“待验证” |

### 三张行动卡

三张卡按依赖顺序排列，每张只包含：

- 目的：它要消除什么不确定性。
- 现在做什么：一个可执行动作。
- 完成标志：应产生什么可检查的记录或客户行为。
- 带回证据：下一次判断需要的原始信息。

### 停止线

分别写明继续、调整和停止的可观察条件。存在客户基线时可引用其口径；不存在时先建立基线，不自行添加数值。

### 回传证据包

完成行动后，按以下结构返回诊断 Skill：

To C 时，`scope` 只填写该规范短标签；分析路径、场景和完整决策放入 `decision`、已确认事实或其他对应证据字段，不得改写 `scope` 中的客群名称。

```yaml
scope: ""
context_stage: ""
action_stage: "K1"
decision: ""
confirmed_facts: []
disconfirmed_assumptions: []
remaining_assumptions: []
customer_actions_observed: []
evidence_gaps: []
stop_line_status: "continue | adjust | stop | unknown"
recommended_next_action: ""
stage_recheck_needed: false
```

只把已发生的客户行为放入 `confirmed_facts` 和 `customer_actions_observed`。

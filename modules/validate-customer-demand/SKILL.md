# K1 找真需求（validate-customer-demand）

> 这是 BMI 业务增长工具箱的八个阶段模块之一，回答「哪一类客户在什么场景下真的会行动」。
> 前置：只有根 `SKILL.md`（业务体检）已确认 `action_stage=K1` 时，才由它加载本模块。本模块不重新诊断阶段，不自行修改 `action_stage`，不调用其他阶段模块。
> 收口：证据补齐后回传业务体检，复核是否进入 K2。

## 概述

把 K1 阶段的模糊兴趣转换为可被验证或推翻的客群、场景、问题和行动证据。本模块不重做阶段诊断，也不提前设计完整产品或投入规模化获客。

## 显性专业价值

K1 必须追问：**谁最愿意为哪一种改变付出行动**。缺少会改变优先 Target 的证据时，先说明为什么不能直接判断，并只问一个决定性问题；不以人口标签或想象出来的客群代替行为证据。

K1 的顾问论点是：**客群不是人口标签**。可行动的细分，是在同一触发场景下、为同一种改变而采取相似行动的人；人口特征只能帮助找到他们，不能证明需求。

完整输出固定写明：`核心判断`、`关键机制`、`为什么不是另一个常见答案`、`改判证据`；行动 HTML 首屏再用 `关键反常识`、`本轮明确不做`、`改判证据` 三格压缩资源取舍。结论要鲜明，证据状态要诚实；不寻常来自机制洞察，不来自冒犯性标签。

## 客户可感知的阶段决策闭环

完整输出时，在任何方法名称或画布之前先放置“阶段决策卡”。卡片固定写明：

- 本阶段唯一决策：应该优先服务哪类客户。
- 为什么暂不进入相邻阶段：目标客群、场景、问题或行动证据仍不稳定时，不进入 K2；新证据推翻原 Target 时，退回本阶段重做选择。
- 30 天最小证据闭环：只验证会改变优先 Target 判断的一项客户行为或替代证据。
- 什么新证据会推翻当前建议：明确记录事实、假设和缺口，不以人口标签、口头兴趣或 STP 图形替代需求证据。

画布只用于呈现收窄过程与定位取舍，不能替代客户行动、停止线或阶段交接。

## 执行约定

用户明确请求优先于默认流程与展示偏好。复用交接证据；完整分析或正式测试已授权本轮分析和本地报告，不逐步重复确认。证据闸门仍须满足，发布、部署和全局同步须另获授权。若本模块规则导致暂停或偏离请求，链接具体规则并说明原因。

## 按需读取

选择验证动作时读取方法，组织完整结果或回传时读取交付契约，生成画布或 HTML 时读取可视化框架；已读取且未变更的资料不重复加载：

- [方法](modules/validate-customer-demand/references/methods.md)：根据当前最大不确定性选择一种验证方法。
- [顾问锐见库](modules/validate-customer-demand/references/consultant-lenses.md)：已有足够行为线索、需要形成鲜明但可推翻的 K1 判断时读取；每次最多选择一个，不展示完整清单。
- [交付契约](modules/validate-customer-demand/references/deliverables.md)：按七部分交付客户细分、Target、验证与回传。
- [可视化框架](modules/validate-customer-demand/references/visual-frameworks.md)：填写默认价值设计画布（K1 客户细分定位），并按最大证据缺口至多选择一张辅助框架。

只在验证或迭代本模块时读取 [评测案例](modules/validate-customer-demand/references/evaluation-cases.md)。

## 输入契约

优先接收版本 `1.0` 交接对象的 `schema_version`、`scope`、`context_stage`、`action_stage`、`decision`、`business_type`、`work_mode`、`confirmed_facts`、`working_assumptions`、`evidence_gaps` 和 `target_30d`。已有的客户、场景、行为、角色与非目标信息放入 `stage_payload` 并直接复用。

若 `action_stage` 不是 K1，不强行执行；返回阶段诊断补齐或修正。

完成后只追加新的客户行为事实、被推翻假设、仍缺证据和 `recommended_review`，交回 `根 `SKILL.md`（业务体检）`。本模块不自行修改 `action_stage`，也不得调用其他阶段模块。

## 工作流

### 1. 识别业务模式并固定本轮对象

先根据 `business_type` 或已有信息识别 To B、To C 或混合业务。无法判断时，只问一个业务类型问题，并将其计入首轮最多 5 问。混合业务先确认本轮分析企业/渠道客户还是最终个人用户；分别保存两侧证据，不用一侧的证据证明另一侧需求。

用一句话写清本轮要决定“继续验证哪类客户的哪个问题”。如果决策仍是“所有人是否需要”，先缩小范围，并记录当前分析路径。

### 2. 对需求证据分层

- 已发生事实：客户实际的处理方式、时间成本、材料、安排、试用、采购或付款行为。
- 弱线索：点赞、赞同、“有兴趣”、笼统抱怨和将来意向。
- 工作假设：对客群、场景、触发条件和不行动代价的暂时解释。
- 证据缺口：下一次行动必须带回的信息。

不把弱线索升级为需求、付费意愿或价值验证。

### 3. 逐问形成候选 Segment

每次只问一个会改变 Segment、Target 或客户问题定位假设的问题，并复用用户已经提供的信息。证据足够时立即输出；否则首轮最多 5 问。第五个回答后先交付可纠正初稿，只有一个证据缺口会实质改变 Target 时，才在初稿后追加一个针对性问题。

按重复出现的使用场景、问题强度、现有替代行为和可触达性形成候选 Segment。每个候选客群先写清身份/状态、任务场景、购买动机和取舍标准，再压缩为对外标签；不用技术路线、购买渠道或产品品类单独命名客群。证据不足时明确写“候选客群”，不将其写成已确认定位。本轮只对优先 Target 设计最小验证，不把备选或暂不选择客群并入同一验证动作。

### 4. 选择一种最小验证方法

只为当前最大的证据缺口选一种方法。对每个动作写清目的、做法、完成标志和应带回的原始证据，不向用户堆叠工具清单。

已有行为线索时，从顾问锐见库最多选择一个最能改变资源取舍的视角，形成 `关键反常识`、`本轮明确不做` 和 `改判证据`。锐见必须标记证据状态；不能从现有证据推出时，写成可推翻假设，并只追问一个会改变判断的问题。不要向客户展示锐见名称或锐见库清单。

在前述细分后作 STP 决策收口：列出优先、备选和暂不选择 Target、每个优先 Target 对应的非目标客户、客户问题定位假设，以及最大证据缺口。Target 逐项经过可衡量、足够价值、可触达、可区分、可行动五项闸门；缺证据时写“缺口”，不用主观分数补齐。To B 候选过宽时，用嵌套细分从企业特征逐层收窄到运营变量、采购方式、情境因素与购买者特征。客户问题定位假设只说明客户在何种情境下要解决什么问题，不提前定义产品/服务、痛点缓解、收益创造或价值主张；这些属于 K2。

### 5. 设定可纠正的停止线

使用可观察行为表达继续、调整或停止条件。用户没有同口径基线时，先建立基线并复盘；不自行生成访谈数、试点数、转化率、周期或财务门槛。

### 6. 交付并回传

按交付契约依次输出七部分结果。完成 Target 初判后，完整交付默认调用 `modules/validate-customer-demand/scripts/render_k1_stp_bullseye.py` 输出 `.html`，生成独立 K1 HTML 行动报告并内嵌 STP 客群收窄画布；只需单独画布时仍可输出 `.svg`。再紧接输出已填写的价值设计画布（K1 客户细分定位）；只在最大证据缺口需要时再输出一张辅助框架，并用一到三句话说明最关键判断和最大证据缺口。图文必须复用同一组事实、假设和缺口；无法运行脚本时，降级为紧凑 Markdown 同心收窄图，不声称已生成 HTML。未知字段写“待验证”，不得原样输出画布模板说明。随后交付三张行动卡、停止线和回传证据包。新证据改变了阶段或决策时，返回业务体检 重新判断。

## 不可越过的边界

- 不用“有兴趣”证明需求成立。
- 不在 K1 交付完整产品方案、规模投放计划或组织改造方案。
- 不因为存量公司或集团成熟，就将新项目认定为需求已验证。
- 不编造客户语录、行为、数据或门槛。

## 完成前自检

- `action_stage` 是否为 K1，并与 `context_stage` 分开？
- 是否选定一个优先 Target，并聚焦一个主要证据缺口？
- 客群标签是否在回答“谁为什么买”，而不只是技术、渠道或品类？
- 是否已识别 To B、To C 或混合业务；混合业务是否只分析本轮选定的一侧？
- 是否每次只问一个会改变 Segment、Target 或客户问题定位假设的问题，并在首轮最多 5 问内交付初稿？
- 是否给出优先、备选、暂不选择 Target、非目标客户和客户问题定位假设，且未越入 K2？
- 优先 Target 是否逐项经过五项有效细分闸门；To B 过宽时是否完成嵌套收窄？
- 是否将事实、弱线索、假设和缺口分开？
- 是否只选择一个顾问锐见，并明确了反常识判断、不做事项和改判证据？
- 是否按七部分交付，并在 Target 初判后紧接显式标题为“价值设计画布（K1 客户细分定位）”的已填写默认画布？
- 完整交付是否生成 K1 HTML、返回可达链接并区分生成验证与视觉验收；生成失败时是否说明正式报告尚未完成；图文是否使用同一组证据？
- 是否最多选择一张辅助框架，且画布内容与正文中的事实、假设和证据缺口一致？
- 是否避免在画布中填写产品/服务、痛点缓解、收益创造或最终价值主张等 K2 内容？
- 是否交付了三张行动卡、停止线和回传证据包；To C 的 `scope` 是否仅使用规范短标签？
- 是否避免了用户未提供的数量、周期、转化率和财务门槛？
